# flight_interface

ROS 2 package for the ground ↔ flight controller link.

- `fc_telemetry` node (#96): polls the FC over MSP, read-only, through the FC USB (`transport:=usb`) or the ESP transparent bridge (`transport:=udp`, UDP 5760). Publishes `/fc/attitude` (`Vector3Stamped`, rad, REP-103) and `/fc/battery` (`BatteryState`). Don't run it together with `flight_interface` and `publish_fc` true: both publish these topics.
- `msp.py`: the MSP v1 client. The bench tools in `scripts/` import it from here.
- `flight_interface` lifecycle node (#103, decisions in `docs/PraticalPlan/02 Decisions/ADR-025 flight_interface Ground Node.md`): `/mission/velocity_target` → backend → drone, drone state → `/flight/state`.
  - Starts unconfigured. `ros2 lifecycle set /flight_interface configure`, then `activate`: setpoints go out only while active, at `rate_hz` (`50.0`; ROS double parameters need the decimal point: `-p rate_hz:=50.0`), and only from a target that arrives after the activation. `deactivate` sends one last zero.
  - Watchdog: no valid drone state for `link_timeout_sec` (0.5 s, never longer) → zero setpoints and `link_ok` false, so `mission_node` goes IDLE. No latch: the way back after the ESP's link failsafe is the operator's `~/resume`. A target older than 0.25 s by the next tick → zero (the rule of `mission_node`'s REQ-SAF-017).
  - A non-zero setpoint also needs the drone to report `STREAMING`, override on, a known mask (the same gate as `mission_node`) and the FC link alive; axes outside the mask are zero (the rule of `mission_node`'s REQ-SAF-018).
  - Services (`std_srvs/Trigger`, from `configure` on): `~/estop`, `~/reset_estop`, `~/resume`, `~/arm_control`.
  - ARM: only the operator's `~/arm_control` leads to `ARM_CONTROL_REQUEST`, with the `mask` parameter (8, 11 or 15, default 8; another value fails `configure`). Refused unless the node is active, not in E-stop, the link is fresh, the FC link is alive and the ESP reports `SESSION_IDLE`. The node never arms by itself, also not after a reconnect or a reset.
  - Resume: `~/resume` is refused unless the node is active, not in E-stop, the link is fresh, the FC link is alive and the ESP reports `LINK_FAILSAFE`. The node never resumes by itself.
  - ARM and RESUME are held (decision K6): the request goes out once 1.5 s of neutral setpoints went out with no gap of 0.1 s, because the ESP refuses both until the FC has acknowledged RC for 1 s (result 4). A request still pending after 3 s, or whose conditions go (state, link, FC, E-stop, a new session), is dropped: ask again. `/flight/state` shows `arm_pending` / `resume_pending` meanwhile.
  - E-stop: sends one neutral setpoint (mode 0, only if setpoints were going out), then `BYE`, so the ESP starts its ADR-004 output at once; then nothing more. Latched on the node: deactivate, cleanup and configure keep it; only `~/reset_estop` clears it. Control then needs a new session, an operator ARM and a new target.
  - The ESP's answers (decision E2): the services reply when the request is accepted; every `ARM_CONTROL_ACK` / `RESUME_ACK` is then logged, a refusal as a warning with its reason (`MASK_MISMATCH`: the ground must not fly; `FC_NOT_ANSWERING`: the FC is silent or has not acknowledged RC for 1 s; `WRONG_STATE`; `RESUME_CONDITION_NOT_MET`).
  - A process restart clears the E-stop latch. The launch file (`ros2 launch flight_interface flight_interface.launch.py`) has no respawn on purpose; after a restart nothing is sent before configure, activate and an operator ARM.
  - ROS stays on this PC (decision E1): unless already set, the launch file runs the node with `ROS_DOMAIN_ID=42` and `ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST` (so does `docker-compose.yml`). Every terminal that talks to it needs the same: `export ROS_DOMAIN_ID=42 ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST`.
  - REQ-SAF-023: tests drive every transition, link loss, E-stop, reset, resume and reconnect and check that no ARM goes out (calls on the backend and frames the fake ESP receives); a static test checks that ARM is built only in `EspBackend.arm_control()`, which only the node's `_send_due_request()` calls, for a request only `~/arm_control` can hold.
  - Backends (`backend` parameter): `loopback` (no drone; reports `SESSION_IDLE` and the FC link alive, so nothing engages but `link_ok` shows) and `esp` (the gateway firmware over `sd_protocol`, `esp_host`, `esp_port` 5759). `esp` needs `pip install -e drone/ground/src/sd_protocol_py` and the PSK in `SEAME_PSK` or `~/.config/seame-drone/secrets.json` (never a ROS parameter; a file the group or others can read gets a warning in the log: `chmod 600` it). A missing PSK, a bad `esp_port` or an `esp_host` that does not resolve fails `configure`. It opens a new session by itself when the old one is gone, never with ARM, and confirms it at once with a read-only `CONFIG_GET` (the ESP drops an unconfirmed pending session after 2 s). If no frame under the new keys comes back within 1 s (a replayed `HELLO_ACK`, or a gateway that lost the session; decision E4, ADR-005), the session is dropped and the handshake done again, never with ARM. A short TCP write closes TCP (a cut frame would break the ESP's framing).
  - `esp` for now: every setpoint goes out as mode 0 (neutral) until the controller exists (decision C1). `mask` is the one the ESP confirmed with `ARM_CONTROL_ACK` OK in this session (`null` before). While the node is inactive it sends nothing, so the ESP sends no `STATE` or `FC_HEALTH` (it answers the address of the last setpoint). The session code is `sd_protocol.ground`.
  - FC link (`fc_link_ok`, decisions E6, E6.1, E6.2): `null` at the start of each session; `false` at once on `EVENT 0x0201` or an `FC_HEALTH` with `fc_alive` 0; `true` on `EVENT 0x0202` or after 250 ms of `FC_HEALTH` all saying `fc_alive` 1; `null` again after 1 s without `FC_HEALTH`. Anything but `true` blocks ARM, RESUME and non-zero setpoints and makes `link_ok` false.
  - `/flight/state` adds `active`, `estop`, `estop_reason`, `resume_pending`, `arm_pending`, `failsafe_output` (the ESP is sending its failsafe output: `EVENT 0x0104` / `0x0102` or `LINK_FAILSAFE`), `fc_link_ok`, `armed` (`FC_HEALTH`'s armed flag, `null` when unknown; `airborne` = armed, decision D1) and `esp_rx_rejected` (the ESP's `STATE.rx_rejected` through `sd_protocol.WrapCounter`, reset every session) to `mission_node`'s fields.
  - `/fc/attitude` and `/fc/battery` (decisions D2, D2.1; `publish_fc`, default true): from the FC values in every `STATE`, through the same conversion as `fc_telemetry` (`telemetry.py`; `frame_id`, `cell_count` as there), with the yaw zeroed at the first sample after each `activate`. Each is published only while `FC_HEALTH` says its value is fresh (attitude under 250 ms, battery under 1 s): `STATE` alone carries zero before the FC's first reply and frozen values after it goes silent.
  - Code: `guard.py` (logic, no ROS), `backends.py`, `esp_backend.py`, `link_node.py`, `telemetry.py` (shared with `fc_telemetry`). Test doubles: `test/fake_esp.py` (an ESP on localhost built on `sd_protocol`, with `FC_HEALTH`, the #188 RC rule and fault controls such as a replayed `HELLO_ACK`).

The topic contract, parameters, exit codes and bench results are in the vault: `docs/PraticalPlan/03 Architecture/Architecture Document.md` §2. Tests: `docs/PraticalPlan/04 CI-CD/Testing Strategy.md` §5 (`fc_telemetry`).

Run: `ros2 run flight_interface fc_telemetry --ros-args -p transport:=udp`, `ros2 launch flight_interface flight_interface.launch.py backend:=esp`
Test: `colcon test --packages-select flight_interface`
